# Работа с agent-travel-playground

Это самостоятельная песочница для тестирования агентов, организующих поездки через MCP.
Перед изменениями прочитайте [требования](docs/requirements.md) и относящиеся к задаче
разделы [README](README.md). Требования описывают поведение продукта; README — использование.

## Структура

- `service/catalog.py` — загрузка и проверка конфигурации.
- `service/travel.py` — операции бронирования и проверка поездки.
- `service/store.py` — доступы, попытки, транзакции, журнал и ведомость.
- `service/server.py` — MCP и HTTP; `service/admin.py` — команды оператора.
- `config/` — примеры мероприятий; `examples/` — необязательные примеры подключения.
- `tests/` — автономные тесты сервиса.

## Правила изменений

- Сохраняйте независимость от учебного курса, notebook, конкретного LLM-провайдера и
  агентного фреймворка. Сервис предоставляет задачи и проверяет результат, не строит план за агента.
- Следуйте границам запроса. Не добавляйте реальные покупки, новые сценарии или инфраструктуру
  из списка возможных расширений без соответствующей задачи пользователя.
- При изменении поведения синхронизируйте требования, README, описания и схемы MCP,
  примеры и относящиеся к изменению тесты. Не выдавайте новое поведение за прежний контракт.
- Изменяя формат БД или JSON, явно учитывайте существующие попытки и сохранённые результаты;
  не удаляйте пользовательские данные и журнал ради прохождения тестов.
- Предпочитайте короткий явный код. Не добавляйте архитектурные слои и зависимости без
  необходимости для поставленной задачи. Секреты и рабочие токены не помещайте в код и отчёты.
- Служебные планы, идеи, аудиты и результаты прогонов храните в `_dev/`. Это вспомогательные
  материалы, не нормативный источник. Принятые требования закрепляйте в `docs/requirements.md`.

## Проверка и передача

Установка и запуск описаны в README. В активированном окружении из корня проекта:

```bash
pip install -r requirements-dev.txt
python service/admin.py check-config
python -m pytest -q
```

Для изменений сервиса выполняйте относящиеся тесты, включая отрицательные случаи;
изменения MCP проверяйте через настоящий локальный HTTP. Для примеров мероприятий
проверяйте не только структуру JSON, но и ожидаемую выполнимость. Тесты работают
с временными БД и токенами; не используйте для них рабочее хранилище.

Для правок только документации достаточно сверки с кодом и проверки ссылок и команд;
не запускайте или не расширяйте тесты без причины. Отличайте тесты сервиса от запуска
реального агента с LLM. В результате сообщайте, что изменилось, что проверено и что
не удалось проверить. Непроверенный Docker или облачный запуск не называйте выполненным.
