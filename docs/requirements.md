# Требования к agent-travel-playground

Согласованная базовая версия: 15.10.2026. Документ определяет поведение продукта и границы
текущего сценария. Команды запуска и настройки находятся в [README](../README.md),
правила разработки — в [AGENTS.md](../AGENTS.md).

## Назначение

Самостоятельная песочница для тестирования агентов, организующих поездки на мероприятия.
Пользователь подключает своего агента, запускает его на заданных условиях и получает
проверяемый результат по состоянию сервиса.

Сервис предоставляет инструменты для агентов и проверяет результат. Выбор предложений, план действий,
исправление ошибок и решение о завершении остаются агенту. MCP-клиент и агентный фреймворк
выбирает пользователь: допустимы собственный клиент и готовая библиотека.
Пример клиента в `examples/` необязателен и не должен решать задачу бронирования.

## Пользовательский процесс

1. Локально пользователь запускает сервис, настраивает мероприятия и получает тестовый токен.
2. Подключает агента, дает на вход запрос и проверяет поведение, меняет конфигурацию и повторяет попытки.
3. Может быть выдано несколько токенов для работы разных агентов в параллель.
4. Агент получает задание на бронирование и через MCP создаёт брони в playground.

Приложение может быть запущено, как локально так и быть опубликованным для общего доступа, например, для проведения соревнований и/или бенчмарков.

## Конфигурация мероприятий

Конфигурация среда производится через json файл конфигурации:
- JSON содержит список мероприятий с уникальными ID, названиями, датами, условиями поездки,
  рейсами и гостиницами. Структуру и поля см. в README; примеры находятся в `config/`.
- Условия включают города отправления и назначения, фиксированные даты вылетов, одного
  пассажира и общий бюджет. Цены — целые неотрицательные числа в учебных рублях.
- Доступность рейсов и отдельных ночей задаётся явно. Во время попытки она фиксирована;
  бронирование не уменьшает общий запас мест. Каталог относится к мероприятию, отдельные
  среды или случайные каталоги на каждого пользователя не требуются.
- Ошибочные поля, типы, даты, цены и повторяющиеся ID отклоняются при загрузке.
  Проверка структуры не обязана искать решение задачи. Поставляемые штатные примеры
  должны быть выполнимы; пользователь может создавать невозможные варианты для тестов.
- Сервер читает конфигурацию при запуске. Начатая попытка сохраняет снимок своих условий;
  изменения файла применяются после перезапуска к новым попыткам. Для повторного опыта
  с изменёнными данными оператор сбрасывает прежнюю попытку.

## Доступ и инструменты

MCP работает через Streamable HTTP с заранее выданным Bearer-токеном. Токен определяет
владельца и назначенное мероприятие; агент не может подменить их аргументами инструмента.
Чужие попытки и брони недоступны. Выпуск, отзыв и перевыпуск токенов, назначение мероприятия
и сброс попытки выполняются оператором, а не инструментами агента.

| Инструмент | Обязательное поведение |
|---|---|
| `start_task` | Создать или вернуть текущую попытку типа `travel` |
| `inspect_task` | Вернуть словесный запрос, сведения о мероприятии и каталоги |
| `book_flight` | Создать бронь доступного рейса |
| `book_hotel` | Создать бронь гостиницы при доступности всех запрошенных ночей |
| `cancel_booking` | Бесплатно отменить свою бронь |
| `list_bookings` | Показать свои брони, статусы и сумму активных броней |
| `finish` | Проверить итоговую поездку и при успехе выдать квитанцию |

Схемы аргументов доступны через `tools/list`. Ошибка операции не должна выглядеть успешной
бронью. Отказ из-за недоступного рейса, занятой ночи или неверных дат не создаёт бронь.
Сервис может принять отдельную доступную бронь, не подходящую для общей поездки:
совместимость всех частей проверяет `finish`.

## Условия успешной поездки

Успех определяется состоянием сервиса. Текст агента «готово», его локальный трейс или
переданный им признак успеха не заменяют проверку. Для успеха одновременно выполняются:

1. Агент прочитал задание через `inspect_task`.
2. Есть ровно три активные брони: рейс туда, одна гостиница и обратный рейс.
3. Города и фиксированные даты вылетов соответствуют запросу; гостиница находится
   в городе назначения.
4. Прибытие происходит до первого дня мероприятия, обратный вылет — после последнего.
5. Заезд совпадает с датой прибытия, выезд — с датой обратного вылета. Покрыты все ночи
   интервала `[заезд, выезд)`, день выезда не оплачивается как дополнительная ночь.
6. Стоимость двух билетов и всех ночей не превышает общий бюджет. Достаточна любая
   допустимая комбинация, поиск абсолютного минимума не требуется.

Пример: прибытие 11 марта, мероприятие 12–13 марта, обратный вылет 14 марта.
Нужны ночи 11, 12 и 13 марта. Два билета по 8000 и три ночи по 4000 дают 28000 рублей.

## Попытки, повторные вызовы и свидетельство результата

- Повтор одинаковой активной брони возвращает прежнюю запись, в том числе при конкурентных
  запросах. Другая гостиница, рейс или даты создают дополнительную бронь.
- Отмена исключает стоимость из активной суммы; запись остаётся в истории. Повтор отмены
  безопасен. Лишние активные брони мешают успешному завершению.
- Неуспешный `finish` возвращает результат проверок и позволяет исправления, пока попытка
  доступна. Успешный `finish` выдаёт `receipt`, привязанный к владельцу и попытке, и закрывает
  её для изменений. Повторный `finish` возвращает тот же receipt в пределах срока доступа
  и попытки; сохранённый результат остаётся доступен оператору в ведомости.
- Перевыпуск токена сохраняет попытку. Сброс создаёт возможность новой попытки с новым ID,
  сохраняя старый журнал; прежняя квитанция не становится результатом новой попытки.
- Состояние, результат и журнал операций сохраняются в SQLite. Изменение состояния и
  запись результата операции выполняются транзакционно; перезапуск не теряет сохранённые брони.
- Оператор получает ведомость и журнал. Подлинный результат определяется записями сервера,
  а не присланным пользователем файлом. Токены доступа не включаются в журнал операций.

Текущие ограничения: попытка действует 2 часа, бюджет — 100 учитываемых вызовов владельца;
доступ по умолчанию действует 168 часов. Точные эксплуатационные настройки описаны в README.
Внутреннее поле `student` — идентификатор владельца доступа; использование вне курса допустимо.
Сервер подтверждает операции под доступом, но не авторство кода, личность или участие LLM.

## Границы версии

Один пассажир, прямые рейсы, одна гостиница, поездка до 14 дней. Даты местные, время суток,
часовые пояса, пересадки, трансферы, визы и реальные тарифы за отмену не моделируются.
Реальных покупок, платежей и интеграций с поставщиками бронирований нет.

Размещение рассчитано на один процесс сервера и постоянное хранилище SQLite. Удалённый
доступ — через HTTPS; локальная разработка допускает HTTP на localhost. Полноценные OAuth,
SSO, совместимость со всеми MCP-клиентами, соревнование за общий запас мест и распределённое
развёртывание не входят в эту версию. Их отсутствие не требует реализации без отдельной задачи.

## Проверка изменений

| Область | Где проверять |
|---|---|
| Конфигурация, назначение, снимок условий, примеры | `tests/test_config.py` |
| Брони, даты, бюджет, отмены, повторы, доступы, квитанции | `tests/test_store.py` |
| Настоящий MCP по HTTP, схемы и границы доступа | `tests/test_http.py` |

Для изменения правил нужны проверка ожидаемого результата и правдоподобный отрицательный
пример. Для новой штатной конфигурации нужно подтвердить существование допустимой поездки.
Тесты сервиса не подтверждают качество LLM-агента; реальная модель, контейнер, облачное
развёртывание и нагрузка проверяются отдельно. В отчёте указывается только выполненная проверка.
